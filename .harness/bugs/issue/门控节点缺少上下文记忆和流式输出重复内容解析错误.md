## 问题描述

### Bug 1: 门控节点缺少上下文记忆
在 `styled_output` 节点的门控模式下，当处理简单问题需要直接回复时，LLM 输入只携带了检索到的记忆和当前用户输入，但**没有携带完整的对话上下文历史**。这导致：
- LLM 无法理解上下文语境，对用户的回复在语义上出现偏差
- 多轮对话中无法正确指代前文内容，影响对话连贯性

### Bug 2: 流式输出重复内容和 JSON 解析错误
在一次完整的对话流程中（`memory_retrieve` → `styled_output` → `plan_execute` → `evaluate` → `styled_output`），前端会接收到两次用户可见内容：
1. `plan_execute` 节点输出的**未风格化原始内容**会先被流式输出
2. 然后 `styled_output` 节点（风格模式）再输出**风格化后的内容**

此外，未风格化内容的末尾经常会多出一个 `{` 字符，这是由于 JSON 解析过程中流式清洗不完整导致的。

## 复现步骤

### Bug 1 复现：
1. 进行多轮对话，前几轮建立了某个话题上下文
2. 在后续轮次中提出需要依赖前文理解的简单问题
3. 观察到门控节点直接回复时，LLM 不理解上下文，回复语义错误

### Bug 2 复现：
1. 提出需要复杂处理的问题（会经过 plan_execute → evaluate → styled_output 流程）
2. 观察前端输出，可以看到：
   - 首先输出一段未经过风格化的原始回复内容
   - 然后再输出一段风格化后的完整回复内容
   - 第一段未风格化内容末尾通常会多出一个 `{` 字符

## 预期行为

### Bug 1 预期：
- 门控节点在直接回复时，LLM 输入应该包含完整的对话历史上下文
- LLM 能够正确理解多轮对话中的指代关系，语义连贯

### Bug 2 预期：
- 在完整流程中，只有最终 `styled_output` 输出的风格化内容应该展示给用户
- `plan_execute` 阶段的内部处理输出不应该流式输出到前端
- 不会出现多余的 `{` 字符

## 实际行为

### Bug 1 实际：
- 门控节点只传递了 `memory`（检索记忆）和 `user_input`（当前输入）给 LLM
- 缺少 `state["messages"]` 对话历史上下文
- LLM 输出语义不连贯，无法理解上下文语境

### Bug 2 实际：
- 前端同时收集 `plan_execute` 和 `styled_output` 节点的 token
- 导致用户看到两次输出：先出未风格化内容，再出风格化内容
- JSON 解析流式清洗时，在 `plan_execute` 输出中检测到 JSON 起始后停止收集，但可能已经输出了部分内容（包括起始的 `{`）
- 用户最终看到界面上有重复内容，且末尾多出一个 `{`
