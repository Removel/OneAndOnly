## 问题描述

### Bug 1: 门控节点缺少上下文记忆
在 `styled_output` 节点的门控模式下，当处理简单问题需要直接回复时，LLM 输入只携带了检索到的记忆和当前用户输入，但**没有携带完整的对话上下文历史**。这导致：
- LLM 无法理解上下文语境，对用户的回复在语义上出现偏差
- 多轮对话中无法正确指代前文内容，影响对话连贯性

### Bug 2: 流式输出重复内容和 JSON 解析错误
在一次完整的对话流程中（`memory_retrieve` → `styled_output` → `plan_execute` → `evaluate` → `styled_output`），前端会接收到两次用户可见内容：
1. `plan_execute` 节点输出的**未风格化原始内容**会先被流式输出
2. 然后 `styled_output` 节点（风格模式）再输出**风格化后的内容**

此外，未风格化内容的末尾经常会多出一个 `{"` 字符，这是由于 JSON 解析过程中流式清洗不完整导致的。

## 复现步骤

### Bug 1 复现：
1. 进行多轮对话，前几轮建立了某个话题上下文
2. 在后续轮次中提出需要依赖前文理解的简单问题
3. 观察到门控节点直接回复时，LLM 不理解上下文，回复语义错误

### Bug 2 复现：
1. 提出需要复杂处理的问题（会经过 plan_execute → evaluate → styled_output 流程）
2. 观察前端输出，可以看到：
   - 首先输出一段未经过风格化的原始回复内容
   - 然后再输出一段风格化后的完整回复内容
   - 第一段未风格化内容末尾通常会多出 `{"` 字符

## 原因分析

### Bug 1: 门控节点缺少上下文记忆

`styled_output` 的门控模式在调用 summarizer 时，只构造了一条新的 `HumanMessage`：

```python
result = summarizer.invoke({"messages": [HumanMessage(content=user_message)]})
```

因此 LangGraph checkpoint 中已有的 `state["messages"]` 对话历史没有进入 LLM 上下文。对于依赖前文指代的简单问题，门控直接回复时会缺少语义上下文。

### Bug 2: 流式输出重复内容和 JSON 解析错误

前端的 `isTokenSourceNode` 同时采集 `plan_execute` 和 `styled_output` 节点的 token，导致内部执行阶段的原始回复先展示给用户，最终风格化回复又在 `done` 事件中覆盖/追加，形成重复内容。

另外 `cleanStreamContent` 在检测 JSON 起始前没有把当前 token 合并进缓冲区，遇到跨 token 的 `{` 时可能漏判，导致界面残留 `{` 或 `{"`。

## 解决方法

### Bug 1: 门控调用携带历史消息

在 `styled_output` 门控模式中，先复制 `state["messages"]`，再追加本次门控提示词：

```python
input_messages = list(state.get("messages", []))
input_messages.append(HumanMessage(content=user_message))
result = summarizer.invoke({"messages": input_messages})
```

这样简单问题直接回复时也能利用历史对话上下文。

### Bug 2: 仅展示最终输出节点，并修正 JSON 检测

前端流式 token 只采集 `styled_output` 节点，不再展示 `plan_execute` 的内部原始输出。

同时调整 JSON 清洗顺序：先将当前 token 合并到 `rawBuffer`，再统一检测 JSON 起始，避免跨 token 漏判。

   - `cleanStreamContent` 改为基于合并后的完整缓冲检测 JSON 起始
